Learning objectives

What you should be able to do

  • name the four baselines and the review at which each is set;
  • state the four functions of configuration management and the question each answers;
  • perform a change impact analysis and report what fraction of the baseline it touches;
  • read a technical performance measure by its trend rather than its current value;
  • say what model-based systems engineering changes, and what it leaves exactly as it was.

Engineering situation

A one-line change and sixty documents

Somebody proposes raising the data-bus rate. It is one number in one interface control document, the hardware supports it, and the meeting takes four minutes.

The change board asks the only question that matters: what else does this touch? Nobody knows. The project controls sixty artefacts — requirements, interface documents, budgets, procedures, models — and the honest answer is that finding out means opening all sixty, because a document baseline has no way to be asked. Twelve of them turn out to be affected. The other forty-eight were read to discover that they were not.

Scope and limits

What these three processes have in common

Configuration management, technical assessment and technical data management are three of the eight processes that the Vee could not draw. They share a property: none of them designs anything. Their entire job is to make sure that the thing being designed, verified and delivered is the same thing at every point.

Without them the left branch and the right branch of the Vee slowly come to describe different systems — the requirement refers to a design that was superseded, the test procedure exercises an interface that changed, the mass budget adds up numbers from three different months. Nothing dramatic happens; the project simply stops being about one system.

Configuration management is not version control. A repository records what changed and when; configuration management records what was agreed, by whom, on what analysis, and against which baseline. A project with immaculate version history and no change board has an accurate record of an uncontrolled design.

The word frozen is misleading and worth correcting. A baseline is not unchangeable; it is changeable only through a defined procedure by a defined authority. The point is not to prevent change — every project changes — but to make sure that when it happens, somebody has asked what else moves.

A number over time

Technical performance measures

A technical performance measure is a quantity the project agrees to watch on every reporting cycle, with a planned profile and a limit. Mass, power, data volume, pointing error, cost per unit: the same quantities that carried margins in Lecture 03, now plotted rather than checked.

Plotting is the whole idea. A single value answers whether the project is legal today; a series answers whether it will be legal at delivery, and those are different questions with different answers more often than not. A measure that has fallen four points at each of the last three milestones is going to keep falling, and the honest report is the slope, not the point.

The rule that follows is uncomfortable in a status meeting: a measure inside its limit whose trend leaves the limit before delivery is a finding today, and treating it as acceptable because the current value is acceptable is how the power margin of Lecture 17 reached three per cent without anyone raising it.

Changing where the truth lives

What MBSE actually changes

Model-based systems engineering moves the authoritative source of truth from a set of documents to a single model, and generates the documents from it as views. The requirement, the function it satisfies, the component it is allocated to, the interface it crosses and the test that closes it are one connected structure rather than five files that happen to agree.

The benefit is not that the model is prettier. It is that the model can be asked. “What depends on the data-bus rate?” is a query with an answer, where a document baseline offers only a reading assignment. That is the entire commercial case, and it is enough.

What MBSE does not change: the model is a baseline and must be configuration-controlled exactly as the documents were; the generated documents are still delivered and still read; and a model containing wrong requirements produces beautifully consistent wrong views. It relocates the truth, it does not verify it.

What else lives in this band. Configuration, assessment and data management are not the only work that runs across the whole Vee. The INCOSE handbook groups fourteen more under specialty engineering: mass properties, reliability, availability and maintainability, system safety, security, resilience, human systems integration, value engineering, and manufacturing and producibility among them. This course has been doing several of these without naming the category — the mass budget of Lecture 03 is mass properties engineering, and the FMEA of Lecture 19 is where reliability and safety meet. Producibility is the one it does not reach, and it is worth knowing that the question can this design actually be made, at rate, by the people and machines available is a systems engineering question with a literature, not an afterthought for the shop floor.

Calculation algorithm

Processing a change request

1Identify the baseline the change affects
2Query or search for every dependent artefact
3Count them, and report the fraction of the baseline touched
4Assess the effect on every technical performance measure
5Assess the effect on the verification matrix
6Take it to the authority that owns that baseline
7Record the decision, the analysis and the date
8Update every affected artefact before the next report

Step two is where document baselines and models genuinely differ, and it is the only step where they differ. Everything else — the authority, the record, the update — is identical whether the truth lives in files or in a model.

Worked example

One change, one trend

1
Scope the change. Raising the data-bus rate touches twelve of the sixty controlled artefacts: four requirements, three interface documents, two budgets and three test procedures. That is \[ \frac{12}{60} = 20\,\% \] of the baseline, moved by one number.
2
Count the cost of finding out. A document baseline cannot be queried, so all sixty are opened to identify the twelve. A model answers the same question directly, and the ratio \[ \frac{60}{12} = 5 \] is the factor by which the search shrinks. Note what it is not: the change is the same size either way, and the twelve artefacts still have to be updated by hand.
3
Check the measures. The change adds mass. Mass margin has been reported at four milestones: 20, 16, 12 and 8 %. Every value has been above the 5 % delivery floor, and every status chart has been green.
4
Read the trend instead. The decrement is \(-4\) points at every step, so the straight line reaches the floor at \[ \frac{8 - 5}{4} = 0.75 \] of the way to the next milestone. The measure is legal today and will not be legal at the next reporting cycle, and that is a finding now, before the change is approved rather than after.
5
Decide. The change board has the analysis it needs: 20 % of the baseline touched, twelve artefacts to update, and a technical performance measure already trending through its floor. None of that says the change is wrong. All of it says what the change costs, which is the only thing a change board is entitled to decide on.
\[ \boxed{ \frac{12}{60} = 20\,\%\ \text{of the baseline},\qquad \frac{60}{12} = 5\times\ \text{search},\qquad \frac{8-5}{4} = 0.75\ \text{milestones to the floor} } \]

Interpretation. Three numbers came out of one four-minute proposal, and the project had none of them before the analysis. The 20 % is the size of the change, which nobody had estimated. The factor of five is the price of not having a model, paid in reading. The 0.75 is the one that should stop the meeting: a measure that has been green at four consecutive milestones is about to stop being green, and it was predictable at every one of them.

Operative rules

At a glance

RuleStatement
A baseline is a decision, not a folderIt records what the project agreed to at a review, and changing it requires the same authority that set it.
No change without impact analysisThe question is never whether the change is good, but what else it touches.
Track the trend, not the valueA measure inside its limit with a slope that leaves the limit before delivery is already a finding.
A model is a baseline tooMBSE moves the authoritative source from documents to a model; it does not remove the need to control it.
Documents do not disappearThey become views generated from the model, and a view that is edited by hand has broken the whole arrangement.
The benefit is the queryThe value of a model is that it can be asked what a change affects, and answer without anyone reading sixty documents.

Common mistakes

What goes wrong

  • Approving a change without an impact analysis. The board decides whether the change is good, which is not the question it is there to answer.
  • Mistaking version control for configuration management. A perfect history of an unapproved design is still an unapproved design.
  • Reporting a technical performance measure as a single value. The value says whether the project is legal today; only the trend says whether it will be legal at delivery.
  • Editing a generated document by hand. The model is no longer the source of truth, and nothing in the tooling will tell you.
  • Believing MBSE removes the need for control. The model is a baseline; an uncontrolled model is an uncontrolled design with better diagrams.
  • Leaving the as-built baseline unwritten. Every approved deviation lives there, and without it nobody can say what was actually delivered.

Objetivos de aprendizaje

Qué deberías poder hacer

  • nombrar las cuatro líneas base y la revisión en que se fija cada una;
  • enunciar las cuatro funciones de la gestión de configuración y la pregunta que responde cada una;
  • hacer un análisis de impacto de cambio y reportar qué fracción de la línea base toca;
  • leer una medida de desempeño técnico por su tendencia y no por su valor actual;
  • decir qué cambia el MBSE, y qué deja exactamente igual.

Situación de ingeniería

Un cambio de una línea y sesenta documentos

Alguien propone subir la tasa del bus de datos. Es un número en un documento de control de interfaz, el hardware lo soporta, y la junta dura cuatro minutos.

El comité de cambios hace la única pregunta que importa: ¿qué más toca esto? Nadie sabe. El proyecto controla sesenta artefactos — requisitos, documentos de interfaz, presupuestos, procedimientos, modelos — y la respuesta honesta es que averiguarlo significa abrir los sesenta, porque a una línea base de documentos no se le puede preguntar. Doce resultan afectados. Los otros cuarenta y ocho se leyeron para descubrir que no lo estaban.

Alcance y límites

Qué tienen en común estos tres procesos

La gestión de configuración, la evaluación técnica y la gestión de datos técnicos son tres de los ocho procesos que la V no podía dibujar. Comparten una propiedad: ninguno diseña nada. Su trabajo entero es asegurar que lo que se diseña, verifica y entrega sea la misma cosa en cada punto.

Sin ellos, la rama izquierda y la derecha de la V describen poco a poco sistemas distintos — el requisito se refiere a un diseño superado, el procedimiento de prueba ejercita una interfaz que cambió, el presupuesto de masa suma números de tres meses distintos. Nada dramático ocurre; el proyecto simplemente deja de tratar de un solo sistema.

La gestión de configuración no es control de versiones. Un repositorio registra qué cambió y cuándo; la gestión de configuración registra qué se acordó, quién lo acordó, con qué análisis y contra cuál línea base. Un proyecto con historial impecable y sin comité de cambios tiene un registro exacto de un diseño sin control.

La palabra congelado engaña y vale corregirla. Una línea base no es inmutable; es mutable sólo por un procedimiento definido y una autoridad definida. El punto no es impedir el cambio — todo proyecto cambia — sino asegurar que cuando ocurra, alguien haya preguntado qué más se mueve.

Un número en el tiempo

Medidas de desempeño técnico

Una medida de desempeño técnico es una cantidad que el proyecto acuerda vigilar en cada ciclo de reporte, con un perfil planeado y un límite. Masa, potencia, volumen de datos, error de apuntamiento, costo unitario: las mismas cantidades que cargaban márgenes en la lecture 03, ahora graficadas y no sólo revisadas.

Graficar es la idea entera. Un valor único responde si el proyecto es legal hoy; una serie responde si lo será en la entrega, y esas son preguntas distintas con respuestas distintas más veces que no. Una medida que ha caído cuatro puntos en cada uno de los tres últimos hitos va a seguir cayendo, y el reporte honesto es la pendiente, no el punto.

La regla que se sigue es incómoda en una junta de estatus: una medida dentro de su límite cuya tendencia lo abandona antes de la entrega es un hallazgo hoy, y tratarla como aceptable porque el valor actual es aceptable es como el margen de potencia de la lecture 17 llegó a tres por ciento sin que nadie lo levantara.

Cambiar dónde vive la verdad

Qué cambia realmente el MBSE

La ingeniería de sistemas basada en modelos mueve la fuente autorizada de verdad de un conjunto de documentos a un modelo único, y genera los documentos de él como vistas. El requisito, la función que satisface, el componente al que se asigna, la interfaz que cruza y la prueba que lo cierra son una estructura conectada y no cinco archivos que casualmente coinciden.

El beneficio no es que el modelo sea más bonito. Es que al modelo se le puede preguntar. «¿Qué depende de la tasa del bus de datos?» es una consulta con respuesta, donde una línea base de documentos ofrece sólo una tarea de lectura. Ese es el argumento comercial entero, y basta.

Lo que el MBSE no cambia: el modelo es una línea base y debe controlarse en configuración igual que los documentos; los documentos generados se siguen entregando y leyendo; y un modelo con requisitos equivocados produce vistas equivocadas bellamente consistentes. Reubica la verdad, no la verifica.

Qué más vive en esta banda. Configuración, evaluación y gestión de datos no son el único trabajo que cruza la V entera. El handbook de INCOSE agrupa catorce más bajo ingeniería de especialidad: propiedades de masa, confiabilidad, disponibilidad y mantenibilidad, seguridad del sistema, seguridad informática, resiliencia, factores humanos, ingeniería de valor, y manufactura y producibilidad entre ellas. Este curso ha estado haciendo varias sin nombrar la categoría — el presupuesto de masa de la lecture 03 es ingeniería de propiedades de masa, y la FMEA de la lecture 19 es donde se encuentran confiabilidad y seguridad. La producibilidad es la que no alcanza, y conviene saber que la pregunta ¿este diseño realmente puede fabricarse, al ritmo requerido, con la gente y las máquinas disponibles? es una pregunta de ingeniería de sistemas con literatura propia, no un pendiente del taller.

Algoritmo de cálculo

Procesar una solicitud de cambio

1Identificar la línea base que el cambio afecta
2Consultar o buscar todo artefacto dependiente
3Contarlos, y reportar la fracción de la línea base tocada
4Evaluar el efecto en toda medida de desempeño técnico
5Evaluar el efecto en la matriz de verificación
6Llevarlo a la autoridad dueña de esa línea base
7Registrar la decisión, el análisis y la fecha
8Actualizar todo artefacto afectado antes del siguiente reporte

El paso dos es donde las líneas base de documentos y los modelos difieren de verdad, y es el único paso donde difieren. Todo lo demás — la autoridad, el registro, la actualización — es idéntico viva la verdad en archivos o en un modelo.

Ejemplo resuelto

Un cambio, una tendencia

1
Acotar el cambio. Subir la tasa del bus de datos toca doce de los sesenta artefactos controlados: cuatro requisitos, tres documentos de interfaz, dos presupuestos y tres procedimientos de prueba. Eso es \[ \frac{12}{60} = 20\,\% \] de la línea base, movido por un número.
2
Contar el costo de averiguarlo. Una línea base de documentos no se puede consultar, así que se abren los sesenta para identificar los doce. Un modelo responde lo mismo directamente, y la razón \[ \frac{60}{12} = 5 \] es el factor en que se encoge la búsqueda. Nota lo que no es: el cambio tiene el mismo tamaño de cualquier modo, y los doce artefactos siguen actualizándose a mano.
3
Revisar las medidas. El cambio añade masa. El margen de masa se ha reportado en cuatro hitos: 20, 16, 12 y 8 %. Todo valor ha estado sobre el piso de entrega de 5 %, y todo tablero ha estado verde.
4
Leer la tendencia en su lugar. El decremento es de \(-4\) puntos en cada paso, así que la recta llega al piso a \[ \frac{8 - 5}{4} = 0.75 \] del camino al siguiente hito. La medida es legal hoy y no lo será en el siguiente ciclo de reporte, y eso es un hallazgo ahora, antes de aprobar el cambio y no después.
5
Decidir. El comité de cambios tiene el análisis que necesita: 20 % de la línea base tocado, doce artefactos que actualizar, y una medida de desempeño técnico que ya tiende a cruzar su piso. Nada de eso dice que el cambio sea malo. Todo eso dice qué cuesta el cambio, que es lo único sobre lo que un comité de cambios tiene derecho a decidir.
\[ \boxed{ \frac{12}{60} = 20\,\%\ \text{de la base},\qquad \frac{60}{12} = 5\times\ \text{b\acute{u}squeda},\qquad \frac{8-5}{4} = 0.75\ \text{hitos al piso} } \]

Interpretación. Tres números salieron de una propuesta de cuatro minutos, y el proyecto no tenía ninguno antes del análisis. El 20 % es el tamaño del cambio, que nadie había estimado. El factor de cinco es el precio de no tener un modelo, pagado en lectura. El 0.75 es el que debería detener la junta: una medida que ha estado verde en cuatro hitos seguidos está por dejar de estarlo, y era predecible en cada uno de ellos.

Reglas operativas

De un vistazo

ReglaEnunciado
Una línea base es una decisión, no una carpetaRegistra lo que el proyecto acordó en una revisión, y cambiarla exige la misma autoridad que la fijó.
Ningún cambio sin análisis de impactoLa pregunta nunca es si el cambio es bueno, sino qué más toca.
Sigue la tendencia, no el valorUna medida dentro de su límite con una pendiente que lo abandona antes de la entrega ya es un hallazgo.
Un modelo también es línea baseEl MBSE mueve la fuente autorizada de documentos a un modelo; no elimina la necesidad de controlarla.
Los documentos no desaparecenSe vuelven vistas generadas del modelo, y una vista editada a mano rompió el arreglo entero.
El beneficio es la consultaEl valor de un modelo es que puede preguntársele qué afecta un cambio, y responde sin que nadie lea sesenta documentos.

Errores comunes

Qué sale mal

  • Aprobar un cambio sin análisis de impacto. El comité decide si el cambio es bueno, que no es la pregunta que le toca responder.
  • Confundir control de versiones con gestión de configuración. Un historial perfecto de un diseño no aprobado sigue siendo un diseño no aprobado.
  • Reportar una medida de desempeño como un valor único. El valor dice si el proyecto es legal hoy; sólo la tendencia dice si lo será en la entrega.
  • Editar a mano un documento generado. El modelo deja de ser la fuente de verdad, y nada en la herramienta te lo dirá.
  • Creer que el MBSE elimina la necesidad de control. El modelo es una línea base; un modelo sin control es un diseño sin control con mejores diagramas.
  • Dejar sin escribir la línea base como construido. Ahí vive toda desviación aprobada, y sin ella nadie puede decir qué se entregó realmente.

Lernziele

Was Sie können sollten

  • die vier Basen und das jeweilige Review benennen;
  • die vier Funktionen des Konfigurationsmanagements und ihre Leitfragen nennen;
  • eine Änderungswirkungsanalyse durchführen und den betroffenen Anteil berichten;
  • eine technische Leistungsgröße am Trend statt am aktuellen Wert lesen;
  • sagen, was MBSE ändert und was es genau so lässt, wie es war.

Ingenieurtechnischer Kontext

Eine einzeilige Änderung und sechzig Dokumente

Jemand schlägt vor, die Datenbusrate zu erhöhen. Es ist eine Zahl in einem Schnittstellendokument, die Hardware trägt es, und die Sitzung dauert vier Minuten.

Das Änderungsgremium stellt die einzig wichtige Frage: Was berührt das sonst? Niemand weiß es. Das Projekt lenkt sechzig Artefakte — Anforderungen, Schnittstellendokumente, Budgets, Prozeduren, Modelle — und die ehrliche Antwort lautet, dass man alle sechzig öffnen muss, denn eine Dokumentenbasis lässt sich nicht befragen. Zwölf sind betroffen. Die anderen achtundvierzig wurden gelesen, um festzustellen, dass sie es nicht sind.

Geltungsbereich und Grenzen

Was diese drei Prozesse gemeinsam haben

Konfigurationsmanagement, technische Bewertung und technisches Datenmanagement sind drei der acht Prozesse, die das V nicht zeichnen konnte. Sie teilen eine Eigenschaft: Keiner entwirft etwas. Ihre ganze Aufgabe ist sicherzustellen, dass das Entworfene, Verifizierte und Gelieferte an jeder Stelle dasselbe ist.

Ohne sie beschreiben linker und rechter Ast allmählich verschiedene Systeme — die Anforderung meint einen überholten Entwurf, die Testprozedur prüft eine geänderte Schnittstelle, das Massenbudget addiert Zahlen aus drei Monaten. Nichts Dramatisches geschieht; das Projekt handelt nur nicht mehr von einem System.

Konfigurationsmanagement ist keine Versionsverwaltung. Ein Repository hält fest, was wann geändert wurde; Konfigurationsmanagement hält fest, was vereinbart wurde, von wem, auf welche Analyse hin und gegen welche Basis. Ein Projekt mit makelloser Historie und ohne Änderungsgremium hat eine exakte Aufzeichnung eines ungelenkten Entwurfs.

Vier Momentaufnahmen

Das Wort eingefroren führt in die Irre. Eine Basis ist nicht unveränderlich, sondern nur über ein definiertes Verfahren durch eine definierte Stelle veränderbar. Es geht nicht darum, Änderungen zu verhindern — jedes Projekt ändert sich —, sondern darum, dass jemand fragt, was sich mitbewegt.

Eine Zahl im Zeitverlauf

Technische Leistungsgrößen

Eine technische Leistungsgröße ist eine Größe, die das Projekt in jedem Berichtszyklus verfolgt, mit geplantem Verlauf und Grenzwert. Masse, Leistung, Datenvolumen, Zielgenauigkeit, Stückkosten: dieselben Größen, die in Vorlesung 03 Reserven trugen — nun aufgetragen statt nur geprüft.

Das Auftragen ist der ganze Gedanke. Ein Einzelwert sagt, ob das Projekt heute zulässig ist; eine Reihe sagt, ob es bei der Lieferung zulässig sein wird — zwei Fragen mit meist verschiedenen Antworten. Eine Größe, die an den letzten drei Meilensteinen je vier Punkte verlor, wird weiter verlieren, und der ehrliche Bericht ist die Steigung, nicht der Punkt.

Die Folgeregel ist in einer Statussitzung unbequem: Eine Größe im Limit, deren Trend das Limit vor der Lieferung verlässt, ist heute ein Befund — und sie wegen des aktuellen Werts hinzunehmen ist der Weg, auf dem die Leistungsreserve aus Vorlesung 17 unbemerkt drei Prozent erreichte.

Den Ort der Wahrheit verlegen

Was MBSE wirklich ändert

Modellbasierte Systemtechnik verlagert die maßgebliche Quelle von Dokumenten in ein einziges Modell und erzeugt die Dokumente daraus als Sichten. Anforderung, erfüllte Funktion, zugeordnete Komponente, gekreuzte Schnittstelle und schließender Test sind eine zusammenhängende Struktur statt fünf zufällig übereinstimmender Dateien.

Der Nutzen ist nicht die Schönheit des Modells, sondern dass man es fragen kann. „Was hängt von der Datenbusrate ab?“ ist eine Abfrage mit Antwort, während eine Dokumentenbasis nur eine Leseaufgabe bietet. Das ist die ganze wirtschaftliche Begründung, und sie genügt.

Was MBSE nicht ändert: Das Modell ist eine Basis und muss genauso gelenkt werden wie zuvor die Dokumente; die erzeugten Dokumente werden weiterhin geliefert und gelesen; und ein Modell mit falschen Anforderungen erzeugt wunderbar konsistente falsche Sichten. Es verlagert die Wahrheit, es prüft sie nicht.

Was sonst in diesem Band lebt. Konfiguration, Bewertung und Datenmanagement sind nicht die einzige Arbeit, die das ganze V durchzieht. Das INCOSE-Handbuch fasst vierzehn weitere unter Spezialdisziplinen zusammen: Masseneigenschaften, Zuverlässigkeit, Verfügbarkeit und Wartbarkeit, Systemsicherheit, IT-Sicherheit, Resilienz, Mensch-System-Integration, Wertanalyse sowie Fertigung und Herstellbarkeit. Dieser Kurs betreibt mehrere davon, ohne die Kategorie zu benennen — das Massenbudget aus Vorlesung 03 ist Masseneigenschaftstechnik, und die FMEA aus Vorlesung 19 ist der Treffpunkt von Zuverlässigkeit und Sicherheit. Die Herstellbarkeit erreicht er nicht, und es lohnt zu wissen, dass die Frage lässt sich dieser Entwurf mit den vorhandenen Menschen und Maschinen tatsächlich in der geforderten Rate fertigen eine systemtechnische Frage mit eigener Literatur ist und keine Nebensache der Werkstatt.

Rechenalgorithmus

Einen Änderungsantrag bearbeiten

1Die betroffene Basis bestimmen
2Jedes abhängige Artefakt abfragen oder suchen
3Sie zählen und den betroffenen Anteil berichten
4Die Wirkung auf jede Leistungsgröße bewerten
5Die Wirkung auf die Verifikationsmatrix bewerten
6Zur zuständigen Stelle dieser Basis bringen
7Entscheidung, Analyse und Datum festhalten
8Alle betroffenen Artefakte vor dem nächsten Bericht aktualisieren

Schritt zwei ist der einzige, in dem sich Dokumentenbasis und Modell wirklich unterscheiden. Alles Übrige — Befugnis, Aufzeichnung, Aktualisierung — ist gleich, ob die Wahrheit in Dateien oder im Modell wohnt.

Rechenbeispiel

Eine Änderung, ein Trend

1
Die Änderung eingrenzen. Die höhere Datenbusrate berührt zwölf der sechzig gelenkten Artefakte: vier Anforderungen, drei Schnittstellendokumente, zwei Budgets und drei Testprozeduren. Das sind \[ \frac{12}{60} = 20\,\% \] der Basis, bewegt von einer Zahl.
2
Die Suchkosten zählen. Eine Dokumentenbasis lässt sich nicht abfragen, also werden alle sechzig geöffnet, um die zwölf zu finden. Ein Modell beantwortet dieselbe Frage direkt, und das Verhältnis \[ \frac{60}{12} = 5 \] ist der Faktor, um den die Suche schrumpft. Beachten Sie, was es nicht ist: Die Änderung bleibt gleich groß, und die zwölf Artefakte sind weiterhin von Hand zu pflegen.
3
Die Kenngrößen prüfen. Die Änderung bringt Masse. Die Massenreserve wurde an vier Meilensteinen berichtet: 20, 16, 12 und 8 %. Jeder Wert lag über der Lieferuntergrenze von 5 %, und jedes Statusbild war grün.
4
Stattdessen den Trend lesen. Die Abnahme beträgt je \(-4\) Punkte, also erreicht die Gerade die Grenze nach \[ \frac{8 - 5}{4} = 0{,}75 \] des Wegs zum nächsten Meilenstein. Die Größe ist heute zulässig und im nächsten Berichtszyklus nicht mehr — ein Befund jetzt, vor der Genehmigung statt danach.
5
Entscheiden. Das Gremium hat seine Analyse: 20 % der Basis betroffen, zwölf Artefakte zu aktualisieren und eine Leistungsgröße, die bereits durch ihre Grenze läuft. Nichts davon sagt, die Änderung sei falsch. Alles davon sagt, was sie kostet — das Einzige, worüber ein Änderungsgremium zu befinden hat.
\[ \boxed{ \frac{12}{60} = 20\,\%\ \text{der Basis},\qquad \frac{60}{12} = 5\times\ \text{Suche},\qquad \frac{8-5}{4} = 0{,}75\ \text{Meilensteine bis zur Grenze} } \]

Deutung. Aus einem vierminütigen Vorschlag kamen drei Zahlen, die das Projekt vor der Analyse nicht hatte. Die 20 % sind die Größe der Änderung, die niemand geschätzt hatte. Der Faktor fünf ist der Preis des fehlenden Modells, in Lesearbeit bezahlt. Die 0,75 sollte die Sitzung anhalten: Eine an vier Meilensteinen grüne Größe hört gleich auf, grün zu sein — und das war an jedem einzelnen vorhersehbar.

Arbeitsregeln

Auf einen Blick

RegelAussage
Eine Basis ist eine Entscheidung, kein OrdnerSie hält fest, was im Review vereinbart wurde; sie zu ändern verlangt dieselbe Befugnis.
Keine Änderung ohne WirkungsanalyseDie Frage ist nie, ob die Änderung gut ist, sondern was sie sonst berührt.
Den Trend verfolgen, nicht den WertEine Größe im Limit mit einer Steigung, die es vor der Lieferung verlässt, ist bereits ein Befund.
Auch ein Modell ist eine BasisMBSE verlagert die maßgebliche Quelle von Dokumenten ins Modell; die Lenkungspflicht bleibt.
Dokumente verschwinden nichtSie werden aus dem Modell erzeugte Sichten; eine von Hand bearbeitete Sicht zerstört das Ganze.
Der Nutzen ist die AbfrageDer Wert eines Modells liegt darin, dass man es fragen kann, was eine Änderung berührt — ohne sechzig Dokumente zu lesen.

Häufige Fehler

Was schiefgeht

  • Eine Änderung ohne Wirkungsanalyse genehmigen. Das Gremium entscheidet, ob sie gut ist — nicht seine Frage.
  • Versionsverwaltung mit Konfigurationsmanagement verwechseln. Eine perfekte Historie eines ungenehmigten Entwurfs bleibt ein ungenehmigter Entwurf.
  • Eine Leistungsgröße als Einzelwert berichten. Der Wert sagt, ob es heute zulässig ist; nur der Trend sagt es für die Lieferung.
  • Ein erzeugtes Dokument von Hand bearbeiten. Das Modell ist nicht mehr die Quelle, und kein Werkzeug sagt es Ihnen.
  • Glauben, MBSE erspare die Lenkung. Das Modell ist eine Basis; ein ungelenktes Modell ist ein ungelenkter Entwurf mit schöneren Diagrammen.
  • Die Wie-gebaut-Basis nicht schreiben. Dort steht jede genehmigte Abweichung; ohne sie kann niemand sagen, was geliefert wurde.
