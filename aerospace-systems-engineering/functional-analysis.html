How to describe what a system must do without naming what it is, how far to decompose before stopping, and why one shared function can decide where the whole verification campaign has to happen.

Learning objectives

What you should be able to do

  • write a function as a verb phrase and recognise a component wearing a function’s label;
  • draw the black-box view and list what crosses the boundary in each direction;
  • decide when to stop decomposing, and justify the stopping point;
  • group functions into logical elements by cohesion rather than by expected hardware;
  • identify functions split across elements and say what that implies for verification.

Engineering situation

The function list that was a parts list

A team presents its functional analysis. The functions are: battery, solar array, flight computer, radio, thermal control, structure. Six items, neatly listed, and not one of them is a function.

What has happened is that the architecture was chosen before the analysis and then written down as though it were the requirement. Every trade study downstream is now comparing variants of one solution, because the alternatives were eliminated in a list nobody recognised as a decision.

Scope and limits

Describing behaviour, not structure

Functional analysis asks what the system must do, in terms that any candidate architecture would have to satisfy. Its product is a set of functions, their inputs and outputs, and the consequence of each one failing. Nothing in it names a component.

The logical architecture then groups those functions into coherent elements — still without hardware. Only after that does functional allocation assign each function to a physical element, which is the next lecture. Keeping the three steps separate is what leaves room for a real trade study.

What functional analysis does not settle. It does not tell you which architecture is better, and it cannot: it deliberately describes the problem in terms that several architectures satisfy. Choosing among them is the decision analysis of Unit V. The value here is that the choice remains available to be made, rather than having been made by accident in a list.

The test that catches it

If you can buy it, it is not a function

Written asWhy it failsWritten as a function
BatteryA component. It answers what exists, not what must happen.Store and supply electrical energy
Thermal controlA subsystem name. The architecture has been chosen inside the function list.Maintain survivable temperatures
Data handlingA noun phrase that hides what is done to the data.Acquire, store and return science data

The check takes a second per line and it is worth applying to every entry: could you place a purchase order for this? If yes, it is a component. A function is something that has to happen, and several very different components could make it happen.

Cohesion, not convenience

Building the logical architecture

Group functions that share information, timing or physical quantity. The test for a good grouping is that the element can be described without referring to the internals of another. The test for a bad one is that the logical diagram has the same boxes as the subsystem diagram — in which case no decomposition happened and the hardware was assumed all along.

Read the matrix by row. A row with one mark is a function one element owns entirely. A row with several marks is a function no single element can deliver, and that has a consequence the next section makes precise.

Calculation algorithm

Doing the analysis

1Write the top function as a verb phrase
2Draw the black box and list what crosses
3Decompose one level, verbs only
4For each function, record inputs, outputs and failure consequence
5Stop where an owner can be named
6Group into logical elements by cohesion
7Mark the allocation matrix and count the split rows

Step four is what makes the rest useful. The failure consequence of each function is the input to the FMEA of Lecture 19, and recording it now costs a sentence per function instead of a workshop later.

Worked example

Seven functions, five elements, two problems

The atmospheric platform decomposes into the seven second-level functions of the matrix above, grouped into five logical elements. Read the matrix and count.

1
Matrix density. Seven functions against five elements gives \(7\times5 = 35\) cells, of which 10 are populated. A sparse matrix is a good sign: it means most functions have a single owner.
2
The split rows. Two functions are marked in more than one element: manage electrical energy, shared between flight-and-power and environment control, and detect and respond to faults, spread across three elements.
3
What that costs. Neither split function can be verified below the level at which all its elements are present. Detect and respond to faults touches three of the five, so its verification is a system-level activity and needs a system-level test article.
4
What to do about it. Fault detection is genuinely cross-cutting and the split is correct; it is a cost to plan for, not a defect to remove. The energy split is worth a second look: if environment control only needs to request power rather than manage it, the function belongs wholly to flight-and-power and one system-level verification disappears.
\[ \boxed{ 35\ \text{cells},\; 10\ \text{populated},\; 2\ \text{split functions} \Rightarrow 2\ \text{system-level verifications} } \]

Interpretation. Counting the split rows takes a minute and produces a schedule item. Every split function is a verification that cannot happen at subsystem level, which means a test article, a facility booking and a place in the integration sequence — all of which are cheap to plan now and expensive to discover at test readiness.

Operative rules

At a glance

RuleStatement
Functions are verbsIf it can be bought, it is not a function. Store and supply energy, not battery.
Start from the black boxFix what crosses the boundary before deciding anything about the inside.
Stop decomposing when an owner can be namedFurther detail before that is guesswork; less leaves requirements unallocatable.
Logical is not physicalGroup functions by cohesion. If the logical diagram equals the subsystem diagram, no decomposition happened.
A split function sets a verification levelA function shared by two elements cannot be verified below the level where both are present.
Count the split functions earlyThey are the ones that will need system-level test articles, and that is a schedule and cost item.

Common mistakes

What goes wrong

  • Listing components as functions. If it can be purchased, it is not a function, and the architecture has been chosen inside the analysis meant to precede it.
  • A logical architecture identical to the subsystem diagram. Same boxes, same names means no decomposition happened.
  • Decomposing to component level. Below the point where an owner can be named, the detail is guesswork that will be rewritten.
  • Stopping too early. Functions so broad that no requirement can be allocated to them leave the allocation to be improvised later.
  • Grouping by expected hardware. Cohesion means shared information, timing or physical quantity — not shared supplier.
  • Ignoring the split rows. Each one is a verification that cannot happen at subsystem level, and finding that out at test readiness is the expensive way.

Objetivos de aprendizaje

Qué deberías poder hacer

  • escribir una función como frase verbal y reconocer un componente con etiqueta de función;
  • dibujar la vista de caja negra y listar lo que cruza la frontera en cada dirección;
  • decidir cuándo dejar de descomponer, y justificar el punto de paro;
  • agrupar funciones en elementos lógicos por cohesión y no por el hardware esperado;
  • identificar funciones divididas entre elementos y decir qué implica eso para la verificación.

Situación de ingeniería

La lista de funciones que era una lista de partes

Un equipo presenta su análisis funcional. Las funciones son: batería, arreglo solar, computadora de vuelo, radio, control térmico, estructura. Seis elementos, bien listados, y ninguno es una función.

Lo que pasó es que la arquitectura se eligió antes del análisis y luego se escribió como si fuera el requisito. Todo estudio de intercambio aguas abajo compara ahora variantes de una sola solución, porque las alternativas se eliminaron en una lista que nadie reconoció como decisión.

Alcance y límites

Describir comportamiento, no estructura

El análisis funcional pregunta qué debe hacer el sistema, en términos que cualquier arquitectura candidata tendría que satisfacer. Su producto es un conjunto de funciones, sus entradas y salidas, y la consecuencia de que cada una falle. Nada en él nombra un componente.

La arquitectura lógica luego agrupa esas funciones en elementos coherentes — todavía sin hardware. Sólo después la asignación funcional adjudica cada función a un elemento físico, que es la siguiente lecture. Mantener los tres pasos separados es lo que deja espacio para un estudio de intercambio real.

Lo que el análisis funcional no resuelve. No te dice qué arquitectura es mejor, y no puede: describe deliberadamente el problema en términos que varias arquitecturas satisfacen. Elegir entre ellas es el análisis de decisión de la Unidad V. El valor aquí es que la elección sigue disponible, en vez de haberse hecho por accidente en una lista.

La prueba que lo atrapa

Si puedes comprarlo, no es una función

BateríaUn componente. Responde qué existe, no qué debe ocurrir.Almacenar y suministrar energía eléctrica

La verificación toma un segundo por renglón y vale la pena aplicarla a cada entrada: ¿podrías levantar una orden de compra de esto? Si sí, es un componente. Una función es algo que tiene que ocurrir, y componentes muy distintos podrían hacerlo ocurrir.

Cohesión, no conveniencia

Construir la arquitectura lógica

Agrupa funciones que comparten información, temporización o cantidad física. La prueba de un buen agrupamiento es que el elemento pueda describirse sin referirse a las entrañas de otro. La prueba de uno malo es que el diagrama lógico tenga las mismas cajas que el de subsistemas — en cuyo caso no hubo descomposición y el hardware se supuso desde el principio.

Lee la matriz por fila. Una fila con una marca es una función que un elemento posee por completo. Una fila con varias marcas es una función que ningún elemento puede entregar solo, y eso tiene una consecuencia que la siguiente sección precisa.

Algoritmo de cálculo

Hacer el análisis

1Escribir la función superior como frase verbal
2Dibujar la caja negra y listar lo que cruza
3Descomponer un nivel, sólo verbos
4Por cada función, registrar entradas, salidas y consecuencia de falla
5Parar donde pueda nombrarse un dueño
6Agrupar en elementos lógicos por cohesión
7Marcar la matriz de asignación y contar las filas divididas

El paso cuatro es lo que hace útil al resto. La consecuencia de falla de cada función es la entrada del FMEA de la lecture 19, y registrarla ahora cuesta una frase por función en vez de un taller después.

Ejemplo resuelto

Siete funciones, cinco elementos, dos problemas

La plataforma atmosférica se descompone en las siete funciones de segundo nivel de la matriz de arriba, agrupadas en cinco elementos lógicos. Lee la matriz y cuenta.

1
Densidad de la matriz. Siete funciones contra cinco elementos dan \(7\times5 = 35\) celdas, de las cuales 10 están pobladas. Una matriz dispersa es buena señal: significa que la mayoría de las funciones tienen un solo dueño.
2
Las filas divididas. Dos funciones están marcadas en más de un elemento: gestionar la energía eléctrica, compartida entre vuelo-y-potencia y control ambiental, y detectar y responder a fallos, repartida en tres elementos.
3
Cuánto cuesta. Ninguna función dividida puede verificarse debajo del nivel donde todos sus elementos están presentes. Detectar y responder a fallos toca tres de los cinco, así que su verificación es una actividad de nivel sistema y necesita un artículo de prueba de ese nivel.
4
Qué hacer. La detección de fallos es genuinamente transversal y la división es correcta; es un costo a planear, no un defecto a quitar. La división de energía merece una segunda mirada: si control ambiental sólo necesita solicitar potencia y no gestionarla, la función pertenece por completo a vuelo-y-potencia y desaparece una verificación de nivel sistema.
\[ \boxed{ 35\ \text{celdas},\; 10\ \text{pobladas},\; 2\ \text{funciones divididas} \Rightarrow 2\ \text{verificaciones de sistema} } \]

Interpretación. Contar las filas divididas toma un minuto y produce un renglón de calendario. Cada función dividida es una verificación que no puede ocurrir a nivel subsistema, lo que significa un artículo de prueba, una reserva de instalación y un lugar en la secuencia de integración — todo barato de planear ahora y caro de descubrir en la preparación de prueba.

Errores comunes

Qué sale mal

  • Listar componentes como funciones. Si puede comprarse, no es una función, y la arquitectura se eligió dentro del análisis que debía precederla.
  • Una arquitectura lógica idéntica al diagrama de subsistemas. Mismas cajas, mismos nombres significa que no hubo descomposición.
  • Descomponer a nivel de componente. Debajo del punto donde puede nombrarse un dueño, el detalle es conjetura que se reescribirá.
  • Parar demasiado pronto. Funciones tan amplias que ningún requisito puede asignárseles dejan la asignación para improvisarse después.
  • Agrupar por el hardware esperado. Cohesión significa información, temporización o cantidad física compartida — no proveedor compartido.
  • Ignorar las filas divididas. Cada una es una verificación que no puede ocurrir a nivel subsistema, y enterarse en la preparación de prueba es la forma cara.

Lernziele

Was Sie können sollten

  • eine Funktion als Verbalphrase schreiben und eine als Funktion etikettierte Komponente erkennen;
  • die Black-Box-Sicht zeichnen und auflisten, was die Grenze in jede Richtung quert;
  • entscheiden, wann die Zerlegung endet, und den Endpunkt begründen;
  • Funktionen nach Kohäsion statt nach erwarteter Hardware zu logischen Elementen gruppieren;
  • über Elemente geteilte Funktionen erkennen und deren Folge für die Verifikation angeben.

Ingenieurtechnischer Kontext

Die Funktionsliste, die eine Stückliste war

Ein Team stellt seine Funktionsanalyse vor. Die Funktionen lauten: Batterie, Solarfeld, Flugrechner, Funkgerät, Thermalregelung, Struktur. Sechs Sätze, sauber aufgelistet, und keiner ist eine Funktion.

Geschehen ist: Die Architektur wurde vor der Analyse gewählt und dann als Anforderung notiert. Jede nachgelagerte Abwägung vergleicht nun Varianten einer Lösung, weil die Alternativen in einer Liste ausschieden, die niemand als Entscheidung erkannte.

Geltungsbereich und Grenzen

Verhalten beschreiben, nicht Struktur

Die Funktionsanalyse fragt, was das System leisten muss, in Begriffen, die jede Kandidatenarchitektur erfüllen müsste. Ihr Ergebnis sind Funktionen, ihre Ein- und Ausgänge und die Folge ihres Ausfalls. Nichts darin nennt eine Komponente.

Die logische Architektur gruppiert diese Funktionen dann in kohärente Elemente — weiterhin ohne Hardware. Erst danach ordnet die Funktionszuordnung jede Funktion einem physischen Element zu, das ist die nächste Vorlesung. Die drei Schritte getrennt zu halten lässt Raum für eine echte Abwägung.

Was die Funktionsanalyse nicht entscheidet. Sie sagt nicht, welche Architektur besser ist, und kann es nicht: Sie beschreibt das Problem bewusst so, dass mehrere Architekturen es erfüllen. Die Wahl trifft die Entscheidungsanalyse der Einheit V. Der Wert liegt darin, dass die Wahl offen bleibt, statt in einer Liste versehentlich getroffen worden zu sein.

Die Prüfung dauert eine Sekunde je Zeile und lohnt sich für jeden Eintrag: Könnten Sie dafür eine Bestellung auslösen? Wenn ja, ist es eine Komponente. Eine Funktion ist etwas, das geschehen muss, und sehr verschiedene Komponenten könnten es bewirken.

Kohäsion, nicht Bequemlichkeit

Die logische Architektur bauen

Gruppieren Sie Funktionen, die Information, Zeitverhalten oder physikalische Größe teilen. Eine gute Gruppierung erkennt man daran, dass sich das Element ohne Bezug auf das Innere eines anderen beschreiben lässt. Eine schlechte daran, dass das logische Diagramm dieselben Kästen hat wie das Teilsystemdiagramm — dann fand keine Zerlegung statt und die Hardware war von Anfang an gesetzt.

Lesen Sie die Matrix zeilenweise. Eine Zeile mit einer Markierung ist eine Funktion, die ein Element ganz besitzt. Eine Zeile mit mehreren ist eine Funktion, die kein Element allein liefert — mit einer Folge, die der nächste Abschnitt präzisiert.

Rechenalgorithmus

Die Analyse durchführen

1Die Oberfunktion als Verbalphrase schreiben
2Die Black Box zeichnen und die Übergänge auflisten
3Eine Ebene zerlegen, nur Verben
4Je Funktion Ein-, Ausgänge und Ausfallfolge erfassen
5Stoppen, wo ein Verantwortlicher benennbar ist
6Nach Kohäsion zu logischen Elementen gruppieren
7Die Zuordnungsmatrix markieren und geteilte Zeilen zählen

Schritt vier macht den Rest brauchbar. Die Ausfallfolge jeder Funktion ist die Eingabe für die FMEA aus Vorlesung 19; sie jetzt zu erfassen kostet einen Satz je Funktion statt später einen Workshop.

Rechenbeispiel

Sieben Funktionen, fünf Elemente, zwei Probleme

Die atmosphärische Plattform zerfällt in die sieben Zweitebenenfunktionen der obigen Matrix, gruppiert in fünf logische Elemente. Lesen und zählen Sie die Matrix.

1
Matrixdichte. Sieben Funktionen gegen fünf Elemente ergeben \(7\times5 = 35\) Zellen, davon 10 belegt. Eine dünn besetzte Matrix ist ein gutes Zeichen: Die meisten Funktionen haben einen einzigen Eigentümer.
2
Die geteilten Zeilen. Zwei Funktionen sind in mehreren Elementen markiert: elektrische Energie verwalten, geteilt zwischen Flug-und-Energie und Umgebungsregelung, und Fehler erkennen und darauf reagieren, verteilt auf drei Elemente.
3
Was das kostet. Keine geteilte Funktion ist unterhalb der Ebene verifizierbar, auf der alle ihre Elemente vorliegen. Fehler erkennen und darauf reagieren berührt drei der fünf, ihre Verifikation ist also eine Systemaktivität und braucht ein Systemprüfmuster.
4
Was zu tun ist. Die Fehlererkennung ist echt querschnittlich, die Teilung korrekt; ein einzuplanender Aufwand, kein zu behebender Mangel. Die Energieteilung verdient einen zweiten Blick: Muss die Umgebungsregelung Energie nur anfordern statt verwalten, gehört die Funktion ganz zu Flug-und-Energie, und eine Systemverifikation entfällt.
\[ \boxed{ 35\ \text{Zellen},\; 10\ \text{belegt},\; 2\ \text{geteilte Funktionen} \Rightarrow 2\ \text{Systemverifikationen} } \]

Deutung. Die geteilten Zeilen zu zählen dauert eine Minute und erzeugt einen Terminposten. Jede geteilte Funktion ist eine Verifikation, die nicht auf Teilsystemebene stattfinden kann — also Prüfmuster, Anlagenbuchung und ein Platz in der Integrationsreihenfolge. Jetzt billig zu planen, bei der Testbereitschaft teuer zu entdecken.

Häufige Fehler

Was schiefgeht

  • Komponenten als Funktionen auflisten. Was kaufbar ist, ist keine Funktion — die Architektur wurde in der Analyse gewählt, die ihr vorausgehen sollte.
  • Eine logische Architektur gleich dem Teilsystemdiagramm. Gleiche Kästen, gleiche Namen heißt: keine Zerlegung.
  • Bis auf Komponentenebene zerlegen. Unterhalb der Benennbarkeit eines Verantwortlichen ist das Detail Raten, das neu geschrieben wird.
  • Zu früh aufhören. So breite Funktionen, dass ihnen keine Anforderung zuordenbar ist, verlagern die Zuordnung ins Improvisierte.
  • Nach erwarteter Hardware gruppieren. Kohäsion heißt geteilte Information, Zeitverhalten oder physikalische Größe — nicht geteilter Lieferant.
  • Die geteilten Zeilen ignorieren. Jede ist eine Verifikation, die nicht auf Teilsystemebene stattfinden kann; das bei der Testbereitschaft zu merken ist der teure Weg.
